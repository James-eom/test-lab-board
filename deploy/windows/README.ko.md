# 시험실 가동현황 — Windows 사내 서버 설치 안내

이 패키지는 현재 로컬 수정본(메뉴 이름 변경, 오늘의 시험 팝업, 상태 입력란 제거 포함)을 복사한 설치용 소스입니다. **실제 서버 설치 완료본이 아닙니다.** Windows 서버 버전·사내 주소·인증서·방화벽 범위를 확인한 뒤 설치하세요. 기존 개발 PC의 데이터와 설정은 변경하지 않습니다.

## 1. 설치 전 확인

- 지원 중인 Windows 서버인지 확인하고 회사의 프로그램 설치 승인을 받습니다. Windows PowerShell 5.1 및 `ScheduledTasks`, `NetTCPIP` 모듈이 필요합니다. 서버 OS가 아직 확인되지 않았다면 먼저 확인합니다.
- 서버용 Node.js **24 LTS**를 공식 배포처에서 시스템 전체에 설치합니다. 기본 경로 `C:\Program Files\nodejs\node.exe`를 사용합니다. 서버 OS가 해당 Node.js 버전을 지원하는지 확인합니다. 이 ZIP에는 Node.js와 node_modules를 넣지 않았습니다. [Node.js 공식 다운로드](https://nodejs.org/en/download).
- 설치 중에는 npm 패키지 저장소 접근이 필요합니다. 사내망 정책으로 차단됐다면 IT 담당자에게 프록시 또는 승인된 사내 npm 저장소 설정을 요청하세요. TLS 검증을 끄지 마세요.
- 앱 설치 위치는 **C:\LabPlanner**, 백업은 **C:\LabPlannerBackups**입니다. 두 폴더를 다른 프로그램의 기존 폴더와 섞지 마세요. 설치 스크립트는 새 설치용이며 기존 작업/설정/백업 폴더가 있으면 중단합니다.
- 사내 DNS 이름(예: `lab.company.internal`, 실제 회사 주소로 교체), 해당 이름용 신뢰 가능한 HTTPS 인증서, 정확한 서버 사내 IP와 허용할 사내 IP 대역을 준비합니다. 공용 인터넷 노출과 공유기 포트포워딩은 하지 않습니다.
- 설치 전 패키지 외부에서 전달받은 ZIP의 SHA-256을 `Get-FileHash`로 비교합니다. 신뢰성을 확인한 ZIP만 차단 해제 후 압축을 풉니다. 사내 실행 정책을 임의로 완화하거나 조직 정책을 우회하지 않습니다.
- 앱 계정은 관리자 포함 최대 6명입니다. 관리자 본인 1명 + 팀원 5명 구성이 가능하며, 기존 DB를 이전하면 기존 계정도 한도에 포함됩니다. 이 버전에는 비밀번호 변경/계정 비활성화 화면이 없으므로 계정 정보와 비밀번호 정책을 미리 정하세요.

## 2. 압축 해제와 데이터 선택

ZIP의 `server.mjs`, `public`, `src`, `deploy` 등이 `C:\LabPlanner` 바로 아래에 오도록 풉니다. `C:\LabPlanner\LabPlanner\server.mjs`처럼 두 겹으로 풀지 마세요.

### 빈 데이터로 새 운영 시작

그대로 3단계를 진행합니다. 운영용 첫 관리자와 팀원 계정을 새로 만들고 공휴일 API 인증키를 다시 등록합니다. 기본 내장 휴일 자료는 유지됩니다.

### 기존 시험·계정·공휴일 API 키를 그대로 이전

**운영 DB와 인증키는 이 ZIP에 포함되지 않습니다.** 소스 ZIP과 분리해서, 회사가 승인한 암호화된 전송 경로로만 옮깁니다. 일반 공유 폴더·메일·GitHub·채팅에 DB를 올리지 마세요.

1. 개발 PC에서 변경 작업을 잠시 중단하고 프로젝트 폴더에서 `npm run backup`을 실행합니다. `Backup verified:`에 표시된 SQLite 백업 파일 하나를 사용합니다. 실행 중인 `lab.sqlite`만 탐색기로 복사하거나 WAL/SHM 파일을 임의로 섞지 마세요.
2. 아직 설치 스크립트를 실행하지 않은 서버의 `C:\LabPlanner\data` 폴더에 백업을 **lab.sqlite**라는 이름으로 복사합니다. 같은 파일이나 `lab.sqlite-wal`·`lab.sqlite-shm`이 이미 있으면 덮어쓰지 말고 이전 설치 여부부터 확인합니다.
3. 3단계 설치 후 기존 계정·시험·공휴일 설정을 확인합니다. 첫 관리자 초기화는 건너뜁니다. 인증키 자체를 로그나 화면으로 출력해 확인하지 마세요.
4. 배포 전까지 새 예약 입력을 중단하여 이전 시점 이후 데이터가 두 PC에 갈라지지 않도록 합니다. 서버 전환 후 개발 PC의 DB를 운영 DB로 계속 사용하지 않습니다. DB에는 계정·세션·API 키가 포함되므로 이전용 파일도 제한된 장소에 보관합니다.

## 3. 설치와 첫 관리자

서버에 RDP 등 회사 승인 방식으로 접속해 **Windows PowerShell을 관리자 권한**으로 실행합니다. 설치 경로를 다시 확인한 후 실행합니다.

```powershell
Set-Location C:\LabPlanner
powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File .\deploy\windows\Install-Server.ps1
```

위 명령의 RemoteSigned는 검토·차단 해제한 패키지를 실행하는 해당 프로세스에만 적용하며 영구 실행 정책을 바꾸지 않습니다. 회사 그룹 정책에 의해 차단되면 우회하지 말고 승인된 서명/실행 방식을 확인합니다. 설치 스크립트는 잠금 파일에 맞춰 운영 의존성을 설치하고, 앱 코드에는 LOCAL SERVICE 읽기 권한, 데이터·백업에는 수정 권한을 부여합니다. 일반 사용자의 DB 접근을 막고 관리자와 SYSTEM의 관리 권한을 유지합니다. 서버의 다른 폴더·IIS·방화벽·절전·시간대 설정은 바꾸지 않습니다.

등록되는 작업은 다음 두 개입니다. 로그아웃 상태에서도 LOCAL SERVICE 계정으로 실행되도록 구성합니다. [Microsoft 작업 계정 문서](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtaskprincipal).

| 작업 | 실행 시점 | 역할 |
|---|---|---|
| LabPlanner-Web | 부팅 시, 설치 직후 1회 시작 | 127.0.0.1:4317에서 앱 실행, 실패 시 1분 간격 최대 3회 재시도 |
| LabPlanner-DailyBackup | 매일 서버 현지 시간 03:00 | 온라인 백업 생성 및 무결성 검사 |

웹 작업은 기본 실행시간 제한을 없애 장기 실행하도록 구성합니다. 백업 작업은 최대 1시간으로 제한합니다. 서버 시간대가 한국시간인지 확인하세요. 스크립트가 OS 시간대를 바꾸지는 않습니다. [Microsoft 작업 설정 문서](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtasksettingsset).

새 DB일 경우, **HTTPS 사이트를 다른 PC에 공개하기 전에** 서버에서 다음을 실행합니다. 관리자 비밀번호는 화면에 표시하지 않고 입력받습니다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File .\deploy\windows\Initialize-Admin.ps1
```

기존 관리자가 있으면 이 스크립트는 계정을 바꾸지 않고 종료합니다. 설치 버전은 보안 쿠키를 사용하므로 브라우저 로그인은 다음 단계의 **HTTPS 주소**에서 합니다. `http://서버IP:4317` 접속이나 일반 HTTP 브라우저 로그인이 안 되는 것은 의도한 설정입니다. `COOKIE_SECURE=0`으로 내려서 우회하지 마세요.

설치 오류가 발생하면 무조건 재실행하지 마세요. 작업이 일부 등록됐을 수 있습니다. 작업 스케줄러와 `C:\LabPlanner\data\logs`를 확인하세요. 최초 설치 전용이며, 기존 작업을 `-Force`로 덮어쓰지 않습니다.

## 4. 사내 HTTPS와 접속 허용 — 필수 수동 단계

이 ZIP에는 인증서·사설키가 없고 HTTPS 사이트나 방화벽을 자동 생성하지 않습니다. 서버의 다른 웹서비스에 영향을 줄 수 있으므로 기존 구성을 확인한 뒤 IT 담당자와 함께 적용하세요.

IIS를 사용하는 경우:

1. IIS와 회사 승인 버전의 **URL Rewrite + Application Request Routing(ARR)**을 준비합니다. ARR 프록시 기능이 필요합니다. 기존 서버 공통 설정을 변경하면 다른 사이트에도 영향이 있을 수 있습니다. [Microsoft 역방향 프록시 안내](https://learn.microsoft.com/en-us/iis/extensions/url-rewrite-module/reverse-proxy-with-url-rewrite-v2-and-application-request-routing).
2. 이 앱만 위한 **별도 호스트명/사이트**를 만들고 회사 인증서를 HTTPS 443 바인딩에 연결합니다. `C:\LabPlanner`를 IIS 웹 루트로 지정하지 마세요. DB와 소스가 있는 폴더를 정적 배포하면 안 됩니다. 대신 빈 전용 프록시 폴더(예: `C:\inetpub\LabPlannerProxy`)를 사용합니다. 하위 경로 `/lab` 배포는 현재 지원하지 않습니다. [IIS 바인딩 문서](https://learn.microsoft.com/en-us/iis/configuration/system.applicationhost/sites/site/bindings/binding/).
3. `iis-web.config.example`을 검토하고 **전용 프록시 폴더**에서 `web.config`로 사용합니다. 요청은 `http://127.0.0.1:4317`로 전달합니다. ARR에서 원래 Host 헤더를 보존하도록 `preserveHostHeader=true`를 확인해야 Origin/CSRF 검사가 정상 동작합니다. 서버 공통 설정을 무심코 덮어쓰지 마세요. 앱은 프록시와 같은 서버에 있어야 합니다.
4. 최초 관리자 등록이 완료됐는지 서버에서 `Invoke-RestMethod http://127.0.0.1:4317/api/status`를 실행해 `setupRequired=False`인지 확인한 뒤 사내 접속을 허용합니다. 프록시 뒤의 요청은 백엔드에서 localhost로 보이므로, 미등록 상태로 외부 PC에 공개하면 안 됩니다.
5. 서버의 사내 IP/전용 사이트에 대해서만 443을 허용하고, 원격 허용 주소는 **회사에서 확인한 사내 IP 대역**으로 제한합니다. 무조건 `Any`, 모든 네트워크 프로필, 인터넷 전체를 허용하는 규칙은 만들지 않습니다. 4317 포트는 열지 않습니다. 기존 443 허용 규칙도 외부에 열려 있지 않은지 확인하세요.
6. 회사 DNS와 인증서 신뢰 체인을 팀원 PC에서 확인합니다. 인증서 경고를 무시하지 않습니다. 팀원에게는 확정된 `https://실제사내호스트명/` 주소만 전달합니다. 이 문서의 예시 주소는 접속 주소가 아닙니다.

앱을 단독으로 실행하는 것만으로는 HTTPS 배포가 끝나지 않습니다. 사내 주소·인증서·프록시 구성이 확정되지 않았다면 팀원 배포를 시작하지 마세요.

## 5. 팀원 계정 5명 등록

HTTPS로 관리자 로그인 → 운영 설정 → 팀원 등록에서 각자 다른 아이디·이름·비밀번호와 `팀원` 권한으로 등록합니다. 관리자 비밀번호나 API 인증키는 공유하지 않습니다. 비밀번호는 개인별 안전한 경로로 전달합니다. 첫 관리자 포함 6명 한도이므로 기존 계정을 확인하세요.

팀원용 전달 문구 예:

> 시험실 가동현황 접속 주소: [확정된 사내 HTTPS 주소]
> 사내망에서 브라우저로 접속한 뒤 개별 계정으로 로그인하세요. 프로그램 설치는 필요 없습니다. 인증서 경고나 로그인 오류가 나면 관리자에게 문의하세요.

## 6. 백업·복구·업데이트

첫 백업을 수동 검증합니다. 예약 작업 실행 요청은 비동기이므로 파일이 생성될 때까지 기다리고 작업 결과도 확인하세요.

```powershell
Start-ScheduledTask -TaskName LabPlanner-DailyBackup
Get-ScheduledTaskInfo -TaskName LabPlanner-DailyBackup
Get-ChildItem C:\LabPlannerBackups
```

- 로그: `C:\LabPlanner\data\logs`. 일별/프로세스 시작일 기준 로그를 기록하며, 장기 실행 로그의 자동 회전/삭제 기능은 없습니다. 작업 스케줄러의 마지막 실행 결과와 함께 확인합니다.
- 백업: `C:\LabPlannerBackups`의 `.sqlite`. 별도 보호된 디스크/회사 백업 체계로 복제하세요. 기본 경로는 같은 C: 드라이브라서 서버 디스크 장애 대비가 되지 않습니다. LOCAL SERVICE는 공유폴더 접근이 제한될 수 있으므로 별도 저장장치 복제는 승인된 백업 계정/회사 백업 시스템으로 구성합니다.
- 자동 삭제/보존기간 설정은 하지 않았습니다. 백업과 로그의 용량을 정기 점검하고 회사 보존 정책을 적용하세요. 폴더 전체를 삭제하는 정리 명령은 제공하지 않습니다.
- 복구: 유지보수 시간에 HTTPS 접속을 차단하고 웹/백업 작업을 중지합니다. 4317 리스너가 종료됐는지도 확인하세요. 현재 DB·WAL·SHM은 보호된 별도 폴더로 보관하고, 검증된 백업 하나를 새 `data\lab.sqlite`로 복원합니다. 새 백업에 이전 WAL/SHM을 섞지 않습니다. `server-config.json`과 로그는 보존합니다. 웹 작업을 다시 시작하고 로그인·시험·이력을 확인한 뒤 접속을 재개합니다. 백업 이후 변경은 사라집니다.
- 업데이트: 기존 서버에서 설치 스크립트를 다시 돌리지 않습니다. 먼저 백업하고 작업을 중지한 후 **기존 코드와 package-lock.json을 별도 보관**합니다. 새 소스 중 data·서버 설정·운영 로그를 제외한 코드만 교체하고 `npm ci --omit=dev --ignore-scripts --no-audit --no-fund`를 실행합니다. 기존 작업은 유지한 채 웹 작업을 다시 시작해 확인합니다. 코드만 되돌리는 것과 DB를 복원하는 것은 별개입니다.

## 7. 배포 완료 판정

- [ ] 서버 실제 OS/Node.js/시간대를 확인했고 첫 관리자가 등록돼 있음
- [ ] HTTPS 인증서 경고가 없고 사내망에서만 접속됨
- [ ] 팀원 5명 각각 로그인·같은 일정 조회·등록·수정 확인
- [ ] 동일 시험 중복 저장 차단·충돌 팝업 확인(배압↔토출/방사음 동시 예약 예외는 유지)
- [ ] 메뉴 이름, 오늘 시험 팝업, 상태 선택란 제거, 변경 사유 필수 확인
- [ ] 기존 데이터/계정/실적/이력과 공휴일 연동 확인
